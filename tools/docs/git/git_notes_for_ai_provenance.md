# Git Notes for AI Provenance

+++

In the era of AI-native development, the boundary between human and machine contributions becomes blurred. While commit messages capture **intent**, they are often too rigid to hold the high-resolution metadata required for true AI provenance (e.g., exact token counts, model versions, and prompt-response ratios).

This guide introduces `git notes` as the primary mechanism for maintaining a "Sidecar" metadata store—allowing AI agents to provide detailed attribution without polluting the source code or the primary commit history.

+++

## **Intro: The "Sidecar" Metadata Pattern**

+++

Traditional Git commits are immutable. If you change a commit message to add metadata, you change the commit hash, which rewrites history and breaks all downstream references.

`git notes` solves this by creating a **parallel metadata store**. It allows you to attach information to a commit without modifying the commit object itself.

| Feature | Standard Commit Message | Git Notes |
|:---|:---|:---|
| **Immutability** | Immutable (Hash changes if message changes) | Mutable (Notes can be edited/deleted) |
| **Storage** | Baked into the commit object | Stored in `refs/notes/commits` |
| **Pollution** | Pollutes `git log` if used for metadata | Hidden by default; requires explicit call |
| **Structure** | Free-text / Conventional Commits | Arbitrary (Plain text, JSON, XML) |
| **Syncing** | Automatic via `push` / `pull` | Explicit via `refs/notes/*` |

+++

## **Technical Architecture: How it Works**

+++

Git notes do not live "inside" the commit. Instead, they live in a separate reference namespace.

### 1. The Detached Reference Model
When a note is added to commit `A`, Git does not modify commit `A`. Instead, it:
1. Creates a new object containing the note content.
2. Creates a "notes commit" that points to this object.
3. Updates a pointer in the `refs/notes/commits` branch.

This map (`Commit SHA` $\rightarrow$ `Note SHA`) allows Git to resolve the note on the fly when requested, while keeping the primary commit graph untouched.

### 2. The Tooling vs. Workflow Distinction
`git notes` is a **tooling feature**, not a **workflow feature**. 
- **Workflow features** (like `branch` or `merge`) are designed for human coordination.
- **Tooling features** (like `notes` or `hooks`) are designed for automation and observability.

By using `git notes`, AI agents can maintain an audit trail that is invisible to the human developer during a standard `git log` session but fully accessible to audit scripts and provenance tools.

+++

## **Implementation: Management & Commands**

+++

### Basic Operations

The following commands allow you to manage the metadata sidecar.

| Action | Command | Purpose |
|:---|:---|:---|
| **Attach** | `git notes add -m "metadata" <hash>` | Links a new note to a specific commit. |
| **Retrieve** | `git notes show <hash>` | Fetches the note associated with the commit. |
| **Audit** | `git notes list` | Lists all commits currently carrying metadata. |
| **Modify** | `git notes edit <hash>` | Opens the note in the system editor for updates. |
| **Purge** | `git notes remove <hash>` | Detaches the note from the commit. |

### Synchronization Across Environments
Because notes live in the `refs/notes/` namespace, they are not transferred by default during standard push/pull operations. To synchronize AI provenance data, you must explicitly target the notes ref:

```bash
# Push AI attribution metadata to remote
git push origin refs/notes/*

# Fetch AI attribution metadata from remote
git fetch origin refs/notes/*:refs/notes/*
```

## **AI Engineering Use Case: Provenance Tracking**

+++

In AI-native projects, `git notes` is used to store **Provenance JSON**. This allows the project lead to answer the question: *"Exactly how much of this feature was generated by the AI?"*

### Example Provenance Note
A typical AI-generated note follows this JSON structure:

```json
{
  "version": 1,
  "generator": "qwen-2.5-coder-32b",
  "files": {
    "src/main.py": {
      "aiChars": 1200,
      "humanChars": 200,
      "percent": 85,
      "surface": "cli"
    }
  },
  "summary": {
    "aiPercent": 85,
    "totalFilesTouched": 1
  }
}
```

### Why this approach is mandatory for High-Trust Systems

1. **Zero Source Pollution:** No `# AI-generated` comments inside the `.py` or `.kt` files.
2. **Non-Destructive Audit:** The audit trail exists alongside the code, not inside it.
3. **Machine-Readable:** A simple script can scan `git notes list` and calculate the "AI-Density" of a release.
4. **Immutable Intent, Mutable Metadata:** The *intent* of the change remains frozen in the commit message, while the *attribution* (which model version was used) can be updated if the provenance tool is refined.

:::{tip} The "Sidecar" Analogy
Think of the commit as the **main application** and the git note as a **sidecar container**. The sidecar provides observability, logging, and metadata without ever modifying the application's internal logic or binary.
:::

## **Verification & Troubleshooting**

+++

### "Why can't I see my notes in `git log`?"
By default, `git log` ignores the notes namespace. To see notes integrated into your logs, use:

```bash
git log --show-notes=*
```

### "I got a `No such file or directory` when running `sdkmanager`"
This is not a git notes issue, but a common Android SDK configuration error. Ensure your `ANDROID_HOME` is set and the `cmdline-tools` are placed in a folder named `latest`.
